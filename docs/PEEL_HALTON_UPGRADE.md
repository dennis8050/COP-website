# Peel Halton Area upgrade — release and migration guide

**Status:** Source-code changes are prepared and the default SMS sending gate is **OFF**. Do not interpret this as a completed production deployment. No AWS resources have been modified or Terraform applied. This upgrade adds migration `002_district_followup.sql` and new EventBridge, Lambda and IAM resources. Review the **actual remote-state plan** before permitting an apply.

## What changed

- Responsive website and tab title: **THE CHURCH OF PENTECOST CANADA – PEEL HALTON AREA**; seven public district pages and a district selector on member login.
- Fixed district IDs: `peel-piwc`, `triumph-piwc`, `brampton-bolton`, `innisfil`, `mississauga-ontario`, `georgetown`, `oakville`. Backend filters on the authenticated user's assigned `district_id`, not on browser-selected values. `ADMIN` is the area administrator; `PASTOR` is district-scoped administrative staff; `STAFF` is a district-scoped reader/check-in operator, and `MEMBER` has personal profile access. Only `ADMIN` can edit user access and see all districts.
- Migration adds district assignments to users/members/services/events/ministries/attendance; creates indexes, attendance finalization/deadlines, district SMS settings, consent/opt-out/exemption flags, exemption records and an idempotent SMS notification history. QR and manual attendance have a district consistency check. Finalized attendance is locked against updates and new scans.
- Admin console shows district filters, member consent and district user assignments, finalization button, district SMS enable switch, delay, timezone, template, absence preview, notification status/history.
- Dedicated SMS follow-up Lambda and role, triggered by an EventBridge rule every 15 minutes. SNS direct-to-phone SMS uses the existing AWS SDK signing dependencies. The worker requires `SMS_SEND_ENABLED=true` AND `district_followup_settings.enabled=true`, a completed finalized service, passed deadline, local end-time + delay, a consenting non-exempt active member, and a valid E.164 phone number. It will not process services older than 24 hours. One unique record per (member, service, notification type) and pre-send claim avoid duplicate initiations after crashes; ambiguous outcomes remain `unknown` and **are not automatically retried**.

## Required manual preparation

1. **Safeguard the original.** Back up production RDS and Terraform state and review the existing resource inventory. This updated ZIP deliberately excludes the original `.git` directory, state snapshots, `.tfplan` files, local `.tfvars`, backend/production credentials, and `node_modules`. Do not upload Terraform state into tickets, chats or repositories. If the original ZIP was distributed, review secret exposure and rotate any compromised credentials.
2. **Test on dev/staging first.** Run `npm ci` on your target operating system, `npm run lint`, `npm test`, and `npm run build`. Then run `terraform -chdir=terraform fmt -recursive`, `terraform -chdir=terraform init -backend-config=environments/dev/backend.hcl`, `terraform -chdir=terraform validate`, and `terraform -chdir=terraform plan -var-file=environments/dev/terraform.tfvars -out=review.tfplan`. Inspect every change, particularly destroy/replace actions. **Never apply an unreviewed production plan.** Build and migration must be rolled forward; `002` has no automated rollback.
3. **Run DB migration in dev/staging:** `npm run db:migrate` for the local database. For deployed AWS, invoke the existing `${project}-${environment}-migrate` Lambda after reviewed infrastructure update, and check the returned `success` and `FunctionError`. The transaction/advisory lock make migration one-time. Do not execute the migration outside a backup/restore plan.
4. **Classify legacy records.** Migration does not guess district assignments. Old users/members/services/events/ministries are deliberately unassigned. The area administrator must assign them using the Users screen (for accounts) and resource Edit screens (for members/services/ministries/events). For large datasets, use a separately reviewed SQL mapping with an audit trail. Cognito-confirmed accounts linked to a previously assigned member inherit that district; new registrations remain unassigned until the administrator verifies their district and updates both the account and member record.
5. **Confirm settings.** Configure service `end_time` and `attendance_deadline_at` (timezone-aware timestamp). Ushers must include both QR scans and authorized manual attendance entries, and administrators must finalize explicitly once the deadline and service have passed. Use valid IANA time zones per district. Pastor/Staff accounts must have the matching assigned district. Only authorized personnel should manage phone numbers and consent.
6. **Configure SMS separately.** Confirm AWS SNS SMS sandbox and destination-country restrictions, phone-number origination identity/sender registration, SMS spending limits, opt-out and consent/anti-spam requirements for Canada, privacy disclosures, and valid E.164 numbers. This implementation does **not** include a receipt webhook; `submitted` only confirms provider API acceptance, not delivery. SNS provider-managed STOP opt-outs must be handled/verified; the portal has explicit consent withdrawal and opt-out controls. Set `sms_send_enabled=true` in an **approved** Terraform change only after testing with consenting recipients. Then enable a district in Attendance Follow-Up. To pause, disable its district setting or revert the global flag in a reviewed deployment.
7. **GitHub deployment:** set GitHub environment variable `FOLLOWUP_FUNCTION` from `module.lambda.followup_name`, alongside existing `API_FUNCTION`, `MIGRATION_FUNCTION`, `PROVISION_FUNCTION`. A deployment must update the new worker package alongside the existing API and maintenance functions. For production, require GitHub Environment reviewers. Verify the scheduled role only has the necessary permissions and monitor CloudWatch logs and SNS spend.

## API endpoints added

`GET /public/districts`; authenticated `GET /districts`, `/districts/:slug`; `POST /auth/district` (required Cognito selected-district verification); `POST /services/:id/finalize`; `GET /followup/settings`, `PUT /followup/settings`, `GET /followup/notifications`, `GET /followup/summary`, `GET /followup/absences?service_id=...`. All follow-up admin endpoints are role-gated and district-scoped. The existing endpoints and routes remain available.

## Operational limits and follow-up work

- SMS sender identity registration, quotas, consent-compliance review, exact scheduling, delivery receipts/status callbacks, provider test-send workflow, safe manual retries of definitive failures, batch/rate limits and integration testing against actual SNS are **not complete** and must be completed before a public rollout. No live SMS messages were sent during this code-only update.
- The EventBridge worker runs every 15 minutes; delivery is **not** exactly 2–3 hours to the minute. It waits until at least the configured 120–10080 minute delay and service finalization. If finalization is late and the service ended more than 24 hours ago, the worker intentionally will not send stale absence notifications.
- Legacy rows with no district are visible only to the main `ADMIN` account and must be assigned. Cross-district membership transfers with historical attendance need operational policy/extra reconciliation.
- A live Terraform plan **cannot** be verified from this archive because remote-state access and AWS credentials are not available. Do not treat a static lint check as infrastructure validation. Restore workflow/environment configuration from protected CI/AWS state rather than uploading secrets into the source ZIP.
